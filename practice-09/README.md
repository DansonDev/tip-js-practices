## 1. Цель и результат

Реализовать сервер чтения задач на Express с разделением маршрутов, валидации, хранилища и предметной логики. API отдаёт категории, список и отдельную задачу, фильтрует по четырём параметрам, возвращает структурированные ошибки, обрабатывает HEAD и OPTIONS. [Методичка и стартовый проект ПР9](https://github.com/adyshkins/TIP-JS/tree/37fd64e6f09e728e60e6304d50eda07c398bbd1c/practices/practice-09)

## 3. Модули и контракт

| Модуль | Что выполняет |
|---|---|
| `server.js` | Проверяет порт и запускает Express на 127.0.0.1. |
| `app.js` | Создаёт экземпляр Express, задаёт CORS и Cache-Control, обрабатывает OPTIONS, подключает маршруты, 404 и обработчик ошибок. |
| `routes.js` | Преобразует HTTP-запрос в вызов хранилища и формирует JSON либо ошибку. |
| `validation.js` | Проверяет идентификаторы, имена, уникальность и значения query-параметров. |
| `store.js` и `data.js` | Хранят исходный набор и создают его отдельные копии для экземпляра приложения. |
| `task-service.js` | Выбирает записи по условиям и находит задачу по полю id без изменения исходного массива. |
| `errors.js` | Сериализует `ApiError`, преобразует ошибку декодирования id, возвращает общий ответ при 500. |

| Запрос | Результат |
|---|---|
| GET /api/health | 200, `{"data":{"status":"ok"}}` |
| GET /api/categories | 200, `{data: category[], meta: {total}}` |
| GET /api/tasks | 200, `{data: task[], meta: {total, filters}}` |
| GET /api/tasks/:id | 200, `{data: task}`; неверный id — 400; отсутствующий — 404 с `details.id` |
| HEAD тех же путей | Статус соответствующего GET и заголовки без тела |
| OPTIONS любого пути | 204 и CORS-заголовки без тела |
| Другие методы известных путей | 405, `Allow: GET, HEAD, OPTIONS` |
| Неизвестный путь | 404 `ROUTE_NOT_FOUND` |

`parsePositiveId` проверяет строку целиком, затем вызывает `Number.isSafeInteger`. Запрос с 4abc получает 400, поэтому начало строки не превращается в существующий id 4. Фильтры читаются из `URLSearchParams`; проход по всем именам выявляет повторы даже с одинаковым значением. Отсутствие `completed` даёт `null`, строка `false` преобразуется в логическое `false`. Условия объединяются через И. Поиск обрезает крайние пробелы, сравнивает через `toLocaleLowerCase('ru-RU')`, сохраняет порядок записей.

В стартовом проекте Chrome показал `NOT_IMPLEMENTED` на `GET /api/tasks`, хотя health уже возвращал `ok`. После подключения валидатора и хранилища тот же путь вернул 200, 12 задач и нормализованные фильтры. Регрессию фиксируют HTTP-тесты пустых и отфильтрованных запросов.

## 6. Контрольные вопросы

1. Синтаксис JavaScript общий. Node.js предоставляет серверный ввод-вывод, файловую систему и процессы; браузер предоставляет DOM и применяет ограничения origin.
2. Express выбирает обработчик по HTTP-методу и пути. Query уточняет выборку внутри обработчика.
3. `req.params` содержит значения из шаблона пути. Query передаётся после `?` и описывает условия запроса.
4. Непустая строка `'false'` при `Boolean` даёт true. Строгое сравнение позволяет получить нужное логическое false.
5. Проверка всей строки исключает лишние символы и нестандартную запись. `isSafeInteger` защищает точность id после преобразования.
6. Запрос списка успешно выполнился, поэтому пустая выборка имеет 200. Отдельная задача по корректному id может отсутствовать и даёт 404.
7. `TASK_NOT_FOUND` относится к существующему маршруту и отсутствующей записи. `ROUTE_NOT_FOUND` относится к неизвестному пути.
8. 405 сообщает, что путь существует, но не принимает данный метод. `Allow` перечисляет доступные методы.
9. `meta.total` — число записей после применения условий.
10. Express обходит middleware в порядке регистрации. CORS и OPTIONS нужны до роутов, 404 — после маршрутов, обработчик ошибок — после обычных middleware.
11. По четырём параметрам `(error, req, res, next)` Express отличает middleware ошибок от обычного.
12. Фабрика позволяет создавать приложение с подставным хранилищем. Тесты могут открыть свободный порт и закрыть сервер для каждого набора.
13. При 500 клиенту достаточно статуса, стабильного кода и общего сообщения. Стек, строки подключения и внутренние сведения остаются на сервере.
14. CORS регулирует чтение браузером между origin. Он не проверяет личность, права и возможности других HTTP-клиентов.
15. В ПР10 понадобятся POST, PATCH и DELETE, проверка тела и разрешённых полей, серверный id, изменение хранилища, статусы 201/204 и актуальные Allow/CORS.

## 7. Вывод

Express распределяет запросы по путям и методам. Валидация отделяет ошибки запроса от пустых результатов, а чистая выборка оставляет исходные данные доступными после любых операций чтения.
