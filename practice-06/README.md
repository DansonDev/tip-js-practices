## 1. Цель и результат

Подключить браузерный список задач к учебному HTTP API: загружать задачи и категории, применять серверные фильтры, создавать и изменять задачи, переключать статус и удалять записи. Реализованы состояния загрузки, готового и пустого списка, ошибки и повторной попытки. Изменения подтверждаются сервером, а конкурирующие загрузки не перезаписывают более новый результат.

Источник: [методичка ПР6](https://github.com/adyshkins/TIP-JS/tree/37fd64e6f09e728e60e6304d50eda07c398bbd1c/practices/practice-06). Использован её starter, включая учебные серверы и адаптер DOM.

## 3. Реализация

### 3.1. HTTP-клиент

В [src/api-client.js](src/api-client.js) транспорт ПР5 расширен методами GET, POST, PATCH, DELETE. `buildUrl` объединяет базовый адрес, путь и кодированные query-параметры, сохраняя `false` и `0`. Для тела применяются `JSON.stringify` и `Content-Type: application/json`; тело GET запрещено до вызова `fetch`.

Порядок обработки: проверить `response.ok`; для HTTP-ошибки сохранить статус, `error.code`, `error.message`, `error.details`; для успешного 204 вернуть `null`; для остальных успешных ответов проверить JSON Content-Type и разобрать JSON. Тело 204 не разбирается.

`ApiError` различает `network`, `http`, `timeout`, `aborted`, `invalid-response`. `AbortSignal.timeout` ограничивает ожидание, `AbortSignal.any` объединяет тайм-аут и внешний сигнал. Ошибки чтения тела также обрабатываются. `fetchFn` передаётся параметром для изолированных проверок.

### 3.2. Предметный API

[src/task-api.js](src/task-api.js) содержит следующие операции.

| Функция | Запрос и результат |
|---|---|
| `getTasks` | GET `/tasks`, `{ tasks, meta }` |
| `getTaskById` | GET `/tasks/:id`, одна задача |
| `getCategories` | GET `/categories`, категории |
| `loadInitialData` | Параллельная загрузка задач и категорий через `Promise.all` |
| `createTask` | POST `/tasks`, задача с серверным id |
| `updateTask` | PATCH `/tasks/:id`, обновлённая задача |
| `setTaskCompleted` | PATCH с полем `completed` |
| `deleteTask` | DELETE `/tasks/:id`, `null` после 204 |
| `resetDemoData` | POST `/debug/reset`, подтверждение сброса |

Функции принимают options с сигналом отмены. Проверяются положительные целые id, допустимые фильтры и их типы, схема задачи и категории, уникальность id, соответствие `meta.total` длине массива. Для отдельной задачи проверяется совпадение id ответа с запрошенным. Неверный ответ превращается в `invalid-response`. Модуль не обращается к DOM.

### 3.3. Форма и карточки

[src/form-validation.js](src/form-validation.js) обрезает пробелы в названии и допускает 1–100 символов. Приоритет — `low`, `medium` или `high`; категория преобразуется из значения формы в число и проверяется по загруженному справочнику. Возвращаются `{ valid, value, errors }`, исходный объект не изменяется. При ошибках запрос не отправляется.

[src/task-view.js](src/task-view.js) строит карточки через `createElement` и `textContent`, записывает `data-task-id`, выводит статус, приоритет и имя категории. Три действия: смена статуса, редактирование, удаление. `replaceChildren` заменяет предыдущий список. Серверное название не интерпретируется как HTML. Готовый `dom-app.js` связывает форму и события с контроллером, показывает ошибки полей и блокирует действия на время мутации.

### 3.4. Состояния и мутации

[src/app-controller.js](src/app-controller.js) получает зависимости `api`, `view` и валидатор через параметры.

```text
start / refresh / applyFilters / успешная мутация
  → loading
  → ready, если есть задачи
  → empty, если массив пуст
  → error, если текущий запрос завершился ошибкой
error → повтор → loading → ready / empty / error
```

Начальная загрузка получает задачи и категории параллельно. После успешной загрузки справочника фильтры запрашивают только задачи. Повтор после первоначальной ошибки снова загружает оба ресурса. Отмена устаревшего запроса не показывается как ошибка.

Контроллер ждёт подтверждения создания, редактирования, смены статуса, удаления или сброса, затем повторяет GET с сохранёнными фильтрами. Сервер назначает id и остаётся источником данных; задачи из `localStorage` не читаются. Редактирование отправляет поля формы, сохраняя существующий `completed`. Флаг `mutationPending` запрещает повторную мутацию; разблокировка находится в `finally`.

### 3.5. Конкурирующие запросы

Каждая загрузка отменяет предыдущий `AbortController` и получает возрастающий номер `generation`. После `await` проверяются номер, сигнал и `destroyed`. Поэтому даже запоздавший результат транспорта, не соблюдающего отмену, не меняет представление. Обработчик ошибки проверяет актуальность так же. `destroy()` отменяет загрузку и запрещает дальнейшее обновление представления.

## 6. Ответы на контрольные вопросы

1. **Почему fetch не отклоняет Promise при 404/500?** HTTP-ответ получен на транспортном уровне. Его статус проверяют через `ok`/`status`; отклонение fetch обычно связано с сетью или отменой.
2. **Порядок проверок ответа?** `response.ok` и HTTP-ошибка, успешный 204, JSON Content-Type, разбор JSON. Затем предметный модуль проверяет схему.
3. **POST и PATCH в этом контракте?** POST `/tasks` создаёт запись из title/priority/categoryId; id и начальный статус задаёт сервер. PATCH `/tasks/:id` меняет переданные разрешённые поля существующей записи.
4. **Зачем 201 и Location?** 201 сообщает о создании, Location указывает адрес нового ресурса. JSON содержит созданную задачу с серверным id.
5. **Почему не вызывать json при 204?** Тело отсутствует; разбор пустой строки даст ошибку при успешном удалении.
6. **Когда нужен preflight и почему не помогает no-cors?** На другом origin методы PATCH/DELETE и JSON Content-Type требуют предварительного OPTIONS. API должен разрешить origin, методы и заголовки. no-cors ограничивает запрос и даёт непрозрачный ответ без доступного статуса и JSON.
7. **Empty и error?** Empty — успешно получен пустой массив; error — актуальные данные получить не удалось. В первом случае меняют фильтры, во втором повторяют запрос.
8. **Почему localStorage не источник?** Актуальный набор хранит API. Независимая копия расходилась бы с серверными фильтрами и мутациями.
9. **Зачем GET после мутации?** Сервер назначает id, нормализует данные; запись может перестать соответствовать фильтру. GET возвращает актуальные список и количество.
10. **Как возникает гонка?** A отправлен раньше B, но отвечает позже. Без проверки актуальности A заменит более новый результат B.
11. **Почему недостаточно AbortController?** Продолжение Promise уже могло попасть в очередь; транспорт может не соблюдать сигнал. Номер запроса дополнительно запрещает устаревшую перерисовку.
12. **Почему отмена не ошибка для пользователя?** Она ожидаема при замене фильтра. Старое сообщение мешало бы новой нормальной загрузке.
13. **Что проверяют клиент и сервер?** Клиент проверяет поля, параметры и схему ответа, быстро сообщает об ошибках. Сервер независимо проверяет тело, типы, поля, id и существование категории: запрос можно отправить в обход формы.
14. **Зачем зависимость view?** Контроллер управляет сценарием без DOM. В проверках представление записывает вызовы, позволяя проверить состояния и порядок действий.
15. **Зачем textContent?** Название — данные. textContent выводит символы буквально, не превращая их в HTML и обработчики событий.
